## Root cause and scoped correction

Installed CSI driver: `juicedata/juicefs-csi-driver:v0.33.0`. Its [`GenMountPodPatch` implementation](https://github.com/juicedata/juicefs-csi-driver/blob/v0.33.0/pkg/config/config.go) merges **all** matching patches in list order. The `merge` function **replaces** `mountOptions` with the final matching list, rather than appending. The earlier PVC-specific ring patch matched, as shown by the custom mount image and host networking, but the later broad `juicefs-sc` capstan3 default replaced the ring option list. Previous fresh DGX Mount Pods therefore used the pinned custom image yet ran with `/mnt/jfs-cache` and **no** `cache-group` or peer flags. This is not a selector failure or a reason to upgrade CSI.

Homelab `clusters/mc.yaml`: move the exact `matchName: model-cache` / `matchStorageClassName: juicefs-sc` patch **to the end** of `mountPodPatch`. Keep all unrelated node-local and Argo PVC defaults. Remove `rdma-network`, `rdma-proto`, and `rdma-fallback` from this ring entry, leaving the fork's default TCP peer transport on port 13910. The previous custom Mount Pod image was `local-registry.registry.svc.cluster.local:5000/homelab/juicefs-gcache-csi:gcache-strict-sharding-arm64@sha256:be6ece264ef6c40e7a8e69e6323df95bc5ba92ac0b9e0522679e858b8cff3440`; it was superseded below. Intended flags include `cache-dir=/mnt/pool/juicefs-ring`, `cache-size=550000`, `cache-group=dgx-model-cache`, `group-listen=:13910`, `group-advertise=auto-c7`, `peer-range-read`, `group-heartbeat=5s`, and `remote-timeout=2s`.

- Homelab commit `c4beed9`, PR [#313](https://github.com/ProjectInitiative/homelab/pull/313), merged as `ddcdae759c015aebde51ac258239058efdcf4b52` to `main`; `dev` was fast-forwarded and pushed.
- `nix run .#generate-manifests` passed; rendered `.direnv/manifests/mc.k8s.yaml` shows target patch last and no RDMA flags. The Argo Application targets chart `0.33.0` with `globalConfig.manageByHelm: true`, `automated.prune/selfHeal: true` and the MC cluster.
- Argo reconciled the live `kube-system/juicefs-csi-driver-config` to resourceVersion `629971860`: ring patch last, no `rdma-*` flags. No CSI driver change was needed.

## First live mount attempt and new blocker

A bounded read-only consumer `gcache-ring-mvp-chronometer` created a fresh chronometer Mount Pod with the custom image and **actual** `cache-group=dgx-model-cache`, `peer-range-read`, TCP/13910, `auto-c7` and `/mnt/pool/juicefs-ring`; the hostPath mount was `/mnt/pool/juicefs-ring`. The fork logged the existing volume UUID `e95bc32e-deae-42ab-8ef5-3f489dcca33f`, PostgreSQL metadata, Garage object store, and four advertised chronometer C7 endpoints. It briefly logged `cache group [dgx-model-cache] joined` before FUSE failed:

`fusermount3: unknown option 'peer-range-read'`.

The mount helper's `-o` parser forwarded `peer-range-read` to FUSE even though it is a JuiceFS flag. The consumer never became Ready. It was deleted, and CSI subsequently removed the failing chronometer Mount Pods; the capstan3 `gate-inspector` Mount Pod was not changed. No model data was read through the failed mount.

**The exact custom-image build provenance needs checking.** Current fork source `cmd/main.go` recognizes `peer-range-read` as a `cli.BoolFlag` in `cmd/flags.go` (the new `TestHandleSysMountArgs` covers the exact `-o` option and passes locally). The pinned running image nevertheless forwarded it to FUSE. Either the image contains a pre-flag build or its actual helper differs from the current fork. Rebuild a verified arm64 image from the intended source SHA, pin the new digest in the exact PVC-scoped homelab patch, let Argo sync, then create a fresh DGX mount. Do **not** enable a mount that fails FUSE or delete the live capstan3 mount. A temporary alternative is to remove only `peer-range-read` for a whole-block ring proof if a safe verified fork image cannot be built; this must be documented as reduced functionality, not called ranged-read success.

## Live registry, shard read, and warmup gate (2026-11-08 15:25–15:36 UTC)

**Registry membership:** a read-only `psql -X -w "$metaurl" -Atc` query inside the existing chronometer Mount Pod against PostgreSQL `jfs_gcache_members`, filtered to `ts > extract(epoch from now())::bigint - 15`, returned *simultaneous* `dgx-model-cache` rows: sextant UUID `1403a8ba-e09f-47fa-bb38-3e9593e0be9d`, `172.16.10.56:13910`, and chronometer UUID `970ffecd-c60d-4a07-af2c-f0ccba9e14b5`, `172.16.8.55:13910`; heartbeat ages 1–4 seconds in the later sample. Both Mount Pods were Ready. These are advertised C7/TCP endpoints, not an independently measured successful peer dial. The metadata URL was expanded **inside** the Mount Pod; never print the credential-bearing value.

**Bounded read:** created `llm-test/gcache-shard-hash-chronometer` on chronometer with `model-cache` mounted `readOnly: true`, `automountServiceAccountToken: false`, CPU limit 500m, memory limit 128 MiB, and `activeDeadlineSeconds: 1200`. Its command first checked a regular file and its exact 1,268,777,088-byte size, then ran `sha256sum` over `/models/.cache/huggingface/hub/models--Mia-AiLab--GLM-5.3-Flash-EXL3-4bpw-TensorFold/snapshots/078455ffe6472f9a52fbc1139f58b9db2881b25c/model-00001-of-00083.safetensors`. Logs reported `f774e1ce0cbd03410da592e9c77169a7545a46899696b1c7af2a2fa95d9ade18`, matching `homelab/llm-test/tensorfold-glm53-v14/04-tensorfold-v14-checksums.yaml`; Pod exited 0 and was deleted. This verifies the **actual file bytes through the existing PVC**, not the read's source tier.

**Before/after metrics and observed tier:** the live chronometer Mount Pod's `http://127.0.0.1:39293/metrics` reported `juicefs_remotecache_gets`, `bytes`, `range_gets`, `range_bytes`, `errors`, `range_errors`, and `juicefs_blockcache_peer_range_hits/bytes` **all 0 both before and after**. Its local `juicefs_blockcache_hit_bytes` reached `1.268777088e+09` (exactly the file size), `blockcache_hits=345`, `blockcache_miss_bytes=0`, `blockcache_writes=0`. Sextant's `http://127.0.0.1:39767/metrics` showed no blockcache hits/misses/writes or remote gets. These are per-Mount-Pod counters, not an isolated cluster-wide object-store accounting; no object-store read counter suitable for positive attribution was found. The complete-shard hash was satisfied from **chronometer's pre-existing local persistent cache**, not from sextant. For example, metadata inode `152727` chunk 0 has big-endian slice ID `936567`, size 64 MiB and 4 MiB blocks. Key `chunks/0/936/936567_0_4194304` existed on **both** chronometer and sextant (`4194816` bytes on sextant, including cache checksum overhead), before any new warmup. Rendezvous `murmur3.StringSum64(uuid + "\\x00" + key)` scores this key chronometer `16755937475188161442` versus sextant `11326156378699450577`: chronometer owns it. Chunk 2 block `936570_0_4194304` scores sextant `13991728261477879828` versus chronometer `9198408308858415704`, yet also already exists on **both** disks. Historic non-ring/previous reads left dual residency; a filename alone does not prove that the current ring served it. `HashPrefix=false` and the cache directory is `/mnt/pool/juicefs-ring/e95bc32e-deae-42ab-8ef5-3f489dcca33f/raw/`.

**Warmup intentionally gated:** `pkg/chunk/cached_store.go` `FillCache` checks `store.bcache.exist(k)` **locally** and calls `store.load(..., cache=true, forceCache=true)` for a miss. `pkg/vfs/fill.go`'s iterator sends slices/ranges to this handler; it does not filter by ring owner. `--fill-group-cache` implements push-on-**upload** (`pkg/gcache/server.go` ringStorage), not an ownership-aware `juicefs warmup`. Therefore a normal full-shard warmup would risk populating the wrong node, duplicating cache residency and defeating strict placement. No warmup was run and **no sextant-to-chronometer NVMe-served peer hit is claimed**. Proving the hit without evicting/deleting pre-existing model blocks requires a safely identified shard block missing locally but present on sextant, a bounded read, before/after owner and client counters, and a defensible ownership-aware full-shard warmup method. Do not evict existing cache files just to manufacture proof.

**Commands and cleanup:** observations used `kubectl get pod -n llm-test ...`, `kubectl logs -n llm-test gcache-shard-hash-chronometer --tail=5`, `ssh chronometer 'sudo -n crictl --runtime-endpoint unix:///run/k3s/containerd/containerd.sock exec <current-mount-container-id> sh -c '\''PGCONNECT_TIMEOUT=5 psql -X -w "$metaurl" -Atc "SELECT group_name,uuid,addr,extract(epoch from now())::bigint-ts FROM jfs_gcache_members WHERE ts > extract(epoch from now())::bigint - 15 ORDER BY uuid"'\'''`, read-only `curl` of the mount metrics endpoints, and read-only `sudo stat`/`find` of specific cache keys on both nodes.
